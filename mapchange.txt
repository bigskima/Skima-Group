I want you to **fully migrate SKIMA’s mapping/location implementation to MapLibre now**. Do not treat this as merely changing one map component. Build the mapping foundation properly so SKIMA can support a premium Uber/Bolt/Glovo-style location and live-tracking experience without being dependent on Google Maps.

The immediate objective is:

**MapLibre becomes SKIMA’s map renderer, while routing, geocoding, tiles, GPS/location, live tracking and dispatch remain independent services behind our own Maps/Location domain.**

Do not create another temporary shell. Implement the real reusable mapping foundation and wire at least one real LPG journey end-to-end.

# 6. Do not build production SKIMA directly on public OSM servers

OpenStreetMap data is open, but the public OSM tile infrastructure is not an unlimited commercial map backend.

Therefore:

Use appropriate free/demo infrastructure for development if necessary, but isolate it behind provider configuration.

Do not hardcode:

`tile.openstreetmap.org`

or public Nominatim endpoints everywhere in the app.

The official OpenStreetMap Foundation specifically states that its public tile servers have limited donated capacity, and its public Nominatim instance has its own usage policy. We must therefore retain the ability to switch or self-host later.

Our goal now is **₦0 development**, not to create a future scaling problem.

# 7. Routing architecture

For the open-source routing path, evaluate **OSRM and/or Valhalla** behind our routing interface.

OSRM is an open-source routing engine using OpenStreetMap road data.

Valhalla is also open source and provides routing plus capabilities such as:

* route calculation
* distance/time matrices
* map matching
* turn-by-turn routing
* multiple travel modes

Do not let the mobile frontend call a routing engine directly everywhere.

Prefer:

Mobile
→ SKIMA backend mapping/routing endpoint
→ configured routing provider

where security, caching, provider switching, quotas and observability justify backend mediation.

The backend response should use a SKIMA-defined normalized route structure.

For example conceptually:

* route ID
* origin
* destination
* waypoints
* encoded/GeoJSON route geometry
* distance meters
* duration seconds
* ETA
* provider
* calculated timestamp
* traffic availability if applicable
* confidence/quality if relevant

Do not leak provider-specific response structures throughout SKIMA.

# 9. Coordinate rules

Use a consistent coordinate convention everywhere.

Be extremely careful because mapping libraries and GeoJSON commonly represent coordinates as:

`[longitude, latitude]`

while developers frequently think in:

`latitude, longitude`.

Create typed helpers/types so these cannot be accidentally reversed.

Do not pass anonymous numeric arrays throughout business logic without clear typing.

Database entities should have unambiguous fields such as:

`latitude`
`longitude`

and transformation to `[longitude, latitude]` should happen at the mapping boundary.

Add tests specifically protecting against lat/lng reversal.

# 13. Driver live location

# 14. Tracking frequency must be intelligent

Do not spam the database every second.

Implement configurable tracking rules based on state.

For example:

* driver offline → no active tracking
* available/idle → low-frequency updates where needed
* assigned and driving to customer → higher frequency
* transporting cylinder → operational tracking frequency
* arriving/stationary → reduced updates
* job completed → stop job tracking

Use movement/distance/time thresholds where practical.

Tracking policy should ultimately be configurable from backend/admin configuration.

Do not hardcode one interval throughout the app.
